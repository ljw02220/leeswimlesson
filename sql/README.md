# Supabase SQL 정리본

앞으로는 아래 5개 쿼리를 관리합니다. 번호는 실행 순서입니다.

| 순서 / SQL Editor 이름 | 파일 | 담당 기능 |
|---|---|---|
| 01 기본 DB | `01-base-schema.sql` | 회원, 수업, 가입 신청, 재무 거래, 보고 테이블과 기본 컬럼/권한 |
| 02 보강 관리 | `02-makeup-management.sql` | 보강 시간표, 신청, 승인/취소, 보강 횟수와 사용 내역 |
| 03 수업 댓글 | `03-lesson-comments.sql` | 댓글, 수업노트 시각, 댓글/수업노트 알림 조회 |
| 04 알림 설정 | `04-notifications.sql` | 휴대폰 구독과 푸시 알림 큐/트리거 |
| 05 입금·보고·동기화 | `05-payments-and-reports.sql` | 입금 알리기, 관리자 확인, 직접 입금 확인, 보고 완료, 결제정보 동기화 |

## 기존 쿼리와의 대응

- 기존 ‘동기화 SQL 저장’ → **05 입금·보고·동기화**로 통합했습니다.
- 기존 ‘알림 설정’ → 푸시 부분은 **04**, 아래에 붙어 있던 `payment_requests`와 입금 함수는 **05**로 분리했습니다.
- 기존 ‘보강관리’ → **02**. 현재 코드가 사용하는 보강 횟수 관리와 승인 수정 함수도 포함했습니다.
- 기존 ‘수업댓글 관리’ → **03**.
- 기존 ‘기본 DB 스키마’ → **01**. 중복 정책 생성은 한 번만 남기고, 현재 앱에 필요한 가입 연결·수업 시작일·단체수업 컬럼을 포함했습니다.

## SQL Editor에서 정리하는 방법

1. 기존 쿼리는 우선 이름 앞에 `이전_`을 붙여 보관합니다.
2. 위 이름으로 새 쿼리 5개를 만듭니다.
3. 각 파일 **전체 내용**을 대응하는 쿼리에 붙여 넣고 저장합니다.
4. 적용할 때는 **01 → 02 → 03 → 04 → 05** 순서로 한 파일씩 전체 실행합니다. 오류가 나면 이후 파일로 넘어가지 말고 오류를 확인합니다.
5. 성공한 후 사이트를 새로고침합니다.

쿼리를 저장하는 것과 실행하는 것은 다릅니다. SQL Editor에 저장한 텍스트를 바꾸거나 지워도 이미 만들어진 DB 테이블/함수가 자동으로 바뀌거나 삭제되지 않습니다.

## 이번 정리의 범위

- 기존 운영 DB에는 자동 적용하지 않았습니다. 이 폴더는 검토하고 실행할 SQL 파일입니다.
- `DROP TABLE`, `TRUNCATE`, 기존 회원/입금/보고 행의 일괄 삭제를 넣지 않았습니다.
- 기존 샘플 회원 추가, 금요일 19시 보강 슬롯 정리, 기존 입금/보고 값 일괄 덮어쓰기 등 일회성 데이터 작업은 제외했습니다.
- 보강 시간표 생성 함수는 유지합니다. 시간표 데이터 생성은 앱이 `ensure_makeup_slots()`를 호출할 때 수행합니다.
- 댓글 이름/과거 수업노트 시각을 채우던 일회성 UPDATE도 제외했습니다. 이미 저장된 값은 유지됩니다.
- 함수가 여러 번 정의돼 있던 부분은 최신 정의 하나만 남겼습니다. 특히 `confirm_member_payment`가 과거 버전으로 돌아가지 않도록 했습니다.
- 기본 RLS의 `authenticated ... access` 범위는 보내주신 기존 설정을 유지합니다. 이 작업은 권한 정책을 새로 설계한 보안 개편이 아닙니다.
- 휴대폰 푸시의 서버 함수, VAPID 키, Database Webhook은 SQL과 별도입니다. 기존 `PUSH-NOTIFICATIONS-SETUP.md`를 참고합니다.
- 루트의 예전 `supabase-*-migration.sql`은 이전 작업 기록으로 유지했습니다. 정리 후에는 같은 기능의 예전 파일을 뒤섞어 실행하지 않습니다.

## 이미 운영 중인 DB

앞의 기능이 이미 설치돼 있고 이번 입금→보고 문제만 반영하려면 **05**가 관련 파일입니다. 단, 기존 결제 요청 테이블 등 선행 기능이 없는 DB에서는 01부터 순서대로 적용해야 합니다.

05에는 새 `admin_confirm_member_payment`와 최신 `complete_personal_payment_report`가 포함돼 있어 별도의 `supabase-payment-report-fix.sql`을 추가로 실행할 필요가 없습니다.

기존 입금 기록을 현재 회원정보에 강제로 맞추는 자동 보정은 하지 않습니다. 이미 어긋난 과거 데이터를 고치려면 대상 내역을 별도로 확인해야 합니다.

## 검증 범위

- PostgreSQL 파서로 5개 파일 전체의 SQL과 PL/pgSQL 함수 문법을 검사했습니다.
- 한 파일당 트랜잭션이 하나인지, 같은 함수가 중복 정의되지 않는지, 최상위 INSERT/UPDATE/DELETE/TRUNCATE가 없는지 확인했습니다.
- 운영 DB에는 실행하지 않았습니다. 실제 Supabase의 기존 컬럼·제약조건·권한과의 호환성 및 함수의 동작은 적용 시 확인이 필요합니다. 신규 설치/재실행이 실제 DB에서 통과했다고 검증한 상태는 아닙니다.

## 2026-11-09 입금 건별 보고 연결 수정

05를 최신 내용으로 다시 실행하면 보고서에 `payment_request_id`를 추가하고, 입금 건 ID 기준으로 보고 완료 여부를 판단할 수 있습니다. `complete_confirmed_payment_report`가 입금 한 건을 보고서 한 건에 연결합니다.

기존 보고서는 회원·입금일·금액이 같고 보고서 생성 전에 확인된 입금에만 연결합니다. 기존 보고서의 날짜·금액은 변경하지 않습니다. 시각이나 금액이 달라 연결할 수 없는 과거 보고서는 자동 추정하지 않습니다.

이후 신규 입금은 회원의 과거 완료 표시나 같은 날짜·금액의 예전 보고서 때문에 숨겨지지 않습니다. 한 회원의 미보고 입금 여러 건도 별도로 표시됩니다. 이 변경을 사용하려면 05 SQL과 새 화면 코드가 모두 필요합니다.
